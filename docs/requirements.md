# 校内ARナビ 要件定義書

- プロジェクト名: 校内ARナビ（仮）
- 対象施設: 延岡工業高等学校
- 版: 1.2（2026-09-09）
- 位置づけ: 既存 school-nav の設計を破棄し、ゼロベースで再定義したもの
- v1.2: 寸法入りの学校施設台帳図面が入手できたため、歩測前提の記述を図面ベースに改めた
- スコープ: 案内先3か所（第1段階）＋ 検証

---

## 1. 背景と目的

### 1.1 課題
来校者（オープンスクール参加者・企業・保護者）が校内で迷う。
現状は当日に案内表示を貼り、職員が誘導しているが、以下の負担がある。

- 案内表示の作成・掲示・撤去が毎回発生する
- 職員が要所に立つ必要があり、人手を取られる
- 「事務室で聞く → 口頭で説明 → 途中で分からなくなる」が起きる

### 1.2 目的
**事務室に来た来校者が、スマホでQRを読むだけで目的地まで自力で行ける状態**を作る。
職員の誘導人員をゼロに近づけることを最終目標とする。

### 1.3 プロジェクトの位置づけ
本プロジェクトは**課題研究の制作物**である。したがって成果物はアプリ本体だけでなく、
以下も含む。

| 成果物 | 内容 |
|---|---|
| ナビアプリ | 来校者が使う本体 |
| 測量ツール | 経路データを現地で作るための自作ツール（本研究の中核） |
| 検証データ | 到達テスト・方位センサー誤差測定の結果 |
| 発表資料 | 上記をまとめたスライド・レポート |

**発表の主軸は「測量ツールを自作したこと」に置く。**
「校内ナビを作った」だけの事例は多いが、
「座標データが作れないという壁にぶつかり、それを作る道具から開発した」という構成は独自性がある。

### 1.4 過去プロジェクトからの教訓（設計に反映すべき前提）
| 教訓 | 出典 | 今回の対応 |
|---|---|---|
| iPhone Safari は WebXR 非対応。空間固定ARは不可能 | 2026-07 検証 | 疑似AR（カメラ映像＋画面オーバーレイ矢印）で確定 |
| A-Frame標準フォントは日本語を描画できない | ar-school-guide | AR空間には図形のみ。文字はすべてDOM側で描画 |
| 鉄骨校舎は磁気が乱れ、方位センサーが信用できない | school-nav | 方位は「建物主軸への4方向スナップ」を基本とし、センサーは補助 |
| 手書き見取り図ベースの模式図座標は実測と合わず、修正が延々と続いた | school-nav | **寸法入りの公的図面から座標を起こす**。方位と距離は座標から計算する（→設計書 §1〜3） |
| 校内ネットワークは Cloudflare Tunnel が遮断される | 2026-07-08 検証 | Tunnel は使わない。Cloudflare Pages（静的ホスティング）を使う |
| 校内Wi-Fi は PC-スマホ間の通信ができない | school-nav | ローカル開発サーバでの実機テストは不可。公開URL経由でテストする |

## 2. 対象ユーザーと利用シーン

### 2.1 来校者（一般利用者）
- **属性**: オープンスクールで来校する中学生とその保護者、企業の採用担当者、地域住民
- **端末**: 自分のスマートフォン（iPhone / Android 混在）
- **前提**:
  - アプリのインストールは求められない（絶対条件）
  - 校内Wi-Fiには繋がない。各自のモバイル回線を使う
  - 操作説明を読む気はない。3タップ以内で目的にたどり着く必要がある
- **利用シーン**: 事務室で受付 → 掲示されたQRを読む → 目的地を選ぶ → 案内に従って歩く

### 2.2 管理者（開発者＝本人）
- **属性**: 本アプリの制作者。校内の構造を把握している
- **端末**: スマートフォン（現地実測時）、Windows PC（データ編集・デプロイ時）
- **利用シーン**:
  - 現地の廊下を実際に歩き、進行方向と距離を記録する
  - 記録したデータをPCに取り込み、経路データとして確定する
  - QRコードを印刷して掲示する

## 3. スコープ

### 3.1 やること
- 事務室を起点とした**3か所**への道案内（第1段階。余力があれば追加）
- QRコードによる現在地確定
- カメラ映像に矢印を重ねる疑似AR案内
- 学校施設台帳の図面から経路データを起こす
- 図面から起こしたデータを現地で照合する「現地検証モード」
- 掲示用QRコードの生成・印刷
- Cloudflare Pages への公開

### 3.2 やらないこと（今回のスコープ外）
| 項目 | 理由 |
|---|---|
| 連続測位（歩いている間ずっと現在地を追う） | 屋内GPSは精度が出ず、PDR（歩行者推測航法）は精度が持たない |
| 空間固定AR（床に矢印が貼り付く） | iPhone Safari で実現不可能 |
| 多言語対応 | 現状の来校者は日本語話者が中心。必要になってから |
| バリアフリー経路（車椅子・エレベータ優先） | データ構造上は拡張可能にしておくが、初版では実装しない |
| ユーザー登録・ログイン | 来校者に登録を求める時点で使われない |
| アクセス解析・利用統計 | 初版では不要。必要なら後から |
| 屋外（グラウンド・体育館・実習棟） | まず校舎内3棟を完成させる |

### 3.3 案内先

起点: **事務室前**

#### 第1段階（必須・まずここまで完成させる）

3か所に絞る。この3ルートで**廊下・曲がり角・渡り廊下・階段のすべてのパターンを網羅できる**ため、
技術的な検証としてはこれで十分成立する。

| # | 目的地 | 経路の特徴 | 検証できる要素 |
|---|---|---|---|
| 1 | 職員室 | 同一階・短距離・直線に近い | 基本の直進案内 |
| 2 | 保健室 | 1号館北西翼・曲がり角あり | 曲がる案内・主軸スナップ |
| 3 | 図書館 | 別棟・渡り廊下＋階段 | 棟移動・階移動・QR再読取 |

#### 第2段階（余力があれば追加）

第1段階が完成し、検証まで終わった時点で時間が残っていれば追加する。
測量作業を繰り返すだけなので、実装の追加は不要。

| # | 目的地 | 備考 |
|---|---|---|
| 4 | 校長室 | 1号館主廊下 |
| 5 | 進路指導室 | 1号館北西翼 |
| 6 | 会議室 | 1号館北西翼 |
| 7 | 視聴覚室 | 図書館棟2F |
| 8 | 音楽室 | 3号館4F |
| 9 | 美術室 | 3号館4F |
| 10 | 体育館 | 屋外経由。要検討 |

**設計上の注意**: 案内先の数はデータ（`campus.json` の `destinations`）だけで決まる。
増やしてもコードの変更は発生しない構造にすること。

## 4. 機能要件

### 4.1 来校者モード

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F-01 | QRスキャン | カメラでQRを読み、現在地を確定する | 必須 |
| F-02 | 目的地選択 | 案内先の一覧から選ぶ。大きなボタン形式 | 必須 |
| F-03 | AR案内表示 | カメラ映像の上に進行方向の矢印を重ねて表示 | 必須 |
| F-04 | ステップ案内 | 「廊下を直進 → 突き当たりを右 → 階段で3階へ」を1手順ずつ表示 | 必須 |
| F-05 | 距離の目安表示 | 「約30m（歩いて40秒）」を各手順に表示 | 必須 |
| F-06 | 途中のQR再読取 | 案内中に別のQRを読むと、そこを新しい現在地として経路を引き直す | 必須 |
| F-07 | 到着判定 | 目的地のQRを読むと「到着しました」を表示 | 必須 |
| F-08 | 目印の表示 | 「消火器の先」「掲示板を過ぎて」など、写真か文言での目印 | 高 |
| F-09 | 地図モード | カメラが使えない端末向けの簡易フロア図表示 | 中 |
| F-10 | 方位センサー連動 | 端末を回すと矢印も回り、常に進行方向を指す | 高 |
| F-11 | ホームへ戻る | いつでも最初からやり直せる | 必須 |

### 4.2 管理者モード（現地検証コンソール）

図面から起こしたデータを現地で確かめ、ズレを直すための道具。
**ゼロから測るのではなく、答え合わせをする。**

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| A-01 | モード認証 | 簡易PINでの保護。来校者が誤って入らないようにする | 必須 |
| A-02 | 平面図プレビュー | 図面座標から平面図を描き、図面PDFと見比べられる | 必須 |
| A-03 | 区間一覧 | 各区間の方位・距離の計算値を一覧表示する | 必須 |
| A-04 | 方位の実測と照合 | 進行方向を向いて記録し、図面計算値との差を表示する | 必須 |
| A-05 | planUpBearing 補正 | 複数区間の測定結果から図面全体の回転補正値を提案する | 必須 |
| A-06 | 主軸スナップ | 実測方位を主軸4方向へ補正し、ずれ量を記録する | 必須 |
| A-07 | QR facing 記録 | QR掲示位置で「QRを正面に見た向き」を実測して保存する | 必須 |
| A-08 | 目印の記録 | その地点の写真撮影とメモ入力 | 高 |
| A-09 | ノード座標の手直し | 図面と現況が違う箇所（増改築など）を修正する | 必須 |
| A-10 | 測定ログの書き出し | 全測定値をCSVで書き出す（検証データになる） | 高 |
| A-11 | データ書き出し／取り込み | 現地での修正をJSONでPCへ持ち帰る | 必須 |
| A-12 | QR生成・印刷 | 各QRポイントの掲示用カードを印刷 | 必須 |
| A-13 | 端末間同期 | スマホでの修正をPCで開ける（Cloudflare KV経由） | 低 |

## 5. 非機能要件

### 5.1 性能
- QR認識: かざしてから1秒以内に認識すること
- 初回表示: モバイル回線で3秒以内
- AR表示中の発熱: 10分間の連続使用で端末が持てなくならないこと（フレーム間引きで対応）

### 5.2 対応環境
| 項目 | 要件 |
|---|---|
| iOS | Safari 16以上（iPhone 11以降を想定） |
| Android | Chrome 最新2バージョン |
| 通信 | モバイル回線（4G）で動作すること |
| 権限 | カメラ（必須）・方位センサー（任意、拒否されても動くこと） |

### 5.3 可用性・運用
- オープンスクール当日に落ちないこと（静的ホスティングで担保）
- 掲示したQRのURLは**変わらないこと**（URLが変わると印刷し直しになる）
- 経路データの修正がQRの貼り替えを伴わないこと

### 5.4 コスト
- **金銭コストゼロで運用できること**（学校事務の承認が不要な範囲）
- 従量課金サービスは使わない
- Cloudflare Pages 無料枠（月500ビルド）で十分

### 5.5 保守性
- 経路データはコードと分離し、JSON1ファイルに集約する
- 校舎の改修・教室の移動があっても、更新された図面から起こし直せば反映できること
- 引き継ぎを想定し、データ形式をドキュメント化する

## 6. 制約条件

| 種別 | 制約 |
|---|---|
| 技術 | iOS SafariはWebXR非対応 → 疑似ARのみ |
| 技術 | カメラ・方位センサーはHTTPS必須 |
| 技術 | 屋内では位置情報（GPS）が使えない |
| 環境 | 開発PCは学校管理端末。Node.jsはポータブル版、ネイティブビルド不可 |
| 環境 | 校内ネットワークはプロキシ経由。Cloudflare Tunnel は遮断される |
| 環境 | 校内Wi-Fi では PC-スマホ間通信ができない → 実機テストは公開URL経由 |
| 物理 | 鉄骨校舎のため磁気コンパスが不安定 |
| 運用 | QRの掲示場所は管理職の許可が必要な可能性がある |

## 7. 受け入れ基準

初版リリースの判定基準。**すべて実機・現地で確認すること。**

- [ ] 事務室前のQRを読んでから、第1段階の3か所すべてに到達できる
- [ ] iPhone実機（Safari）でカメラと矢印が動作する
- [ ] Android実機（Chrome）でカメラと矢印が動作する
- [ ] 方位センサーを拒否しても案内が成立する
- [ ] 校内を実際に歩き、矢印が指す方向が実際の進行方向と一致する
- [ ] 案内文が実際の景色と一致する（「右手に消火器」が本当に右手にある）
- [ ] 第三者（アプリを知らない人）が説明なしで目的地に到達できる
- [ ] 掲示用QRが印刷され、実際に掲示できる状態になっている

## 8. 検証計画（課題研究の成果として実施）

アプリの完成とは別に、**測って数字にする**作業を成果に含める。
案内先が3か所でも実施できる内容にしてある。

### 8.1 到達テスト

| 項目 | 内容 |
|---|---|
| 目的 | アプリが実際に道案内として機能するかの定量評価 |
| 方法 | 校舎に不慣れな人 5〜10名に、アプリのみで目的地まで歩いてもらう |
| 測定値 | 到達成功率 / 所要時間 / 迷った回数 / 詰まった地点 |
| 比較対象 | アプリなし（口頭説明のみ）の場合の所要時間 |
| 記録 | 詰まった地点は地図上にプロットし、案内文の改善に反映する |

### 8.2 方位センサー誤差の測定

| 項目 | 内容 |
|---|---|
| 目的 | 鉄骨造校舎で磁気コンパスがどれだけ狂うかを実測し、主軸スナップ方式の妥当性を示す |
| 方法 | 校内の各測定点で、既知の方位を向いた状態のセンサー値を10回ずつ記録 |
| 測定値 | 真値との差（度）/ ばらつき（標準偏差） |
| 成果物 | 誤差の分布グラフ / 校内の誤差マップ（誤差が大きい場所の可視化） |
| 期待される結論 | 「誤差は最大±N度であり、45度の許容幅を持つ4方向スナップなら誤判定は起きない」 |

> 測定点の例: 廊下中央 / 階段室 / 分電盤の近く / 渡り廊下（屋外に近い） / 窓際
> 鉄骨や電気設備の近くで誤差が増える傾向が出れば、そのまま考察になる。

### 8.3 図面値と実測値の照合（本研究の独自性）

| 項目 | 内容 |
|---|---|
| 目的 | 公的図面から起こしたナビゲーションデータが、現況とどれだけ一致するかの評価 |
| 方法 | 距離はメジャー、方位は端末センサーで実測し、図面からの計算値と比較する |
| 測定値 | 距離の誤差率（%）／方位の差（度）／`planUpBearing` の補正量 |
| 期待される結論 | 「歩測せずとも、公的図面から実用精度のナビゲーションデータが作れる」 |

## 10. 用語定義

| 用語 | 意味 |
|---|---|
| ノード | 経路上の地点。部屋・曲がり角・階段の踊り場など |
| エッジ | ノード間のつながり。方位と距離を持つ |
| QRポイント | QRコードを実際に掲示するノード。全ノードのうち一部のみ |
| 主軸方位 | 校舎の長辺が向いている実方位。すべての廊下方位の基準になる |
| 疑似AR | カメラ映像の上に画面座標でオーバーレイを重ねる方式。空間固定はしない |
| 実測モード | 現地を歩きながら方位・距離を記録する管理者向け機能 |
