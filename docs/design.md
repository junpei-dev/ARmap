## 1. 設計の3原則

### 原則1: 座標は図面から取る。歩測はしない

**根拠となる一次資料**: `29_R7延岡工業_図面.pdf`（文部科学省 学校施設台帳 令和7年度）

- 9ページ。ページ1が施設配置図（1/1600）、ページ3以降が各棟の平面図（1/600）
- **全部屋の寸法がメートル単位で記載されている**（例: 職員室 18.00m、校長室 9.00m、事務室 9.00m）
- 廊下幅・階段位置・便所位置も記載されている

前プロジェクト（school-nav）が失敗したのは、**手書き見取り図から起こした不正確な座標**を
使ったためであって、座標方式そのものが悪かったわけではない。
図面の数値は歩測より正確なので、座標を持つ方が明らかに良い。

```
前回: 手書き図から座標を推測 → 実測と合わない → 延々と手直し
今回: 図面の寸法を転記      → 最初から正確   → 現地では方位だけ確認
```

### 原則2: 方位と距離はデータに持たず、座標から計算する

エッジは「AとBがつながっている」という接続関係だけを持つ。
方位も距離も、両端ノードの座標から実行時に計算する。

こうすると、座標を1か所直せば方位も距離も案内文も自動的に追従する。
**同じ情報を2か所に持たない。**

### 原則3: 案内は区間単位で完結させる

QRを読んだ地点から次の分岐点までを1区間とし、区間ごとに独立して案内する。
連続測位はしない。

## 2. 座標系と方位

### 2.1 図面座標系

図面の紙面をそのまま座標系として使う。

```
x : 図面の右方向がプラス（メートル）
y : 図面の下方向がプラス（メートル）
原点: 管理・教室棟①の1階平面図の左上角
```

y が下向きなのは、SVGの画面座標系とそのまま一致させて描画を単純にするため。

### 2.2 実方位への変換

図面の方位記号（ページ1左下）は**右上45度の矢印**で、そこが北。
つまり **図面の上方向 = 北西 = 315度**。

```
図面の上 → 315度（北西）
図面の右 →  45度（北東）
図面の下 → 135度（南東）
図面の左 → 225度（南西）
```

これを `meta.planUpBearing = 315` として持つ。

```ts
/** ノードAからBへの実方位（北=0度、時計回り） */
function bearingOf(a: Node, b: Node, planUpBearing: number): number {
  const dx = b.x - a.x;
  const dy = b.y - a.y;
  // 図面上の角度（図面の上を0度とし、時計回り）
  const planAngle = (Math.atan2(dx, -dy) * 180) / Math.PI;
  return ((planAngle + planUpBearing) % 360 + 360) % 360;
}

/** 水平距離（メートル） */
function distanceOf(a: Node, b: Node): number {
  return Math.hypot(b.x - a.x, b.y - a.y);
}
```

### 2.3 planUpBearing の精度について

施設台帳の方位記号は45度刻みで描かれる慣習があり、**概略値の可能性がある**。

- 初期値は図面どおり **315度** とする
- 現地で方位センサーを使って検証し、ズレていれば `planUpBearing` を1つ直すだけで
  **全ルートの矢印が一斉に補正される**
- Googleマップ・航空写真での確認も併用する

**この1つの数値が全体の精度を決める。** 現地検証の最優先項目。

### 2.4 方位の4方向スナップ（現地検証時のみ）

校舎は直交グリッドなので、廊下の向きは `planUpBearing` から 0/90/180/270 のいずれか。
現地でセンサー値を記録する際、最寄りの4方向にスナップして誤差を評価する。

```ts
function snapToAxis(measured: number, axisBearing: number) {
  const candidates = [0, 90, 180, 270].map((d) => (axisBearing + d) % 360);
  let best = candidates[0];
  let minDiff = 360;
  for (const c of candidates) {
    const diff = Math.abs(((measured - c + 540) % 360) - 180);
    if (diff < minDiff) { minDiff = diff; best = c; }
  }
  return { snapped: best, deviation: minDiff };
}
```

`deviation` の分布が、そのまま「鉄骨校舎における方位センサー誤差」の検証データになる。

## 3. データモデル

### 3.1 全体構造

```jsonc
{
  "version": 2,
  "meta": {
    "school": "延岡工業高等学校",
    "planUpBearing": 315,       // 図面の上方向の実方位（現地検証で補正する）
    "source": "29_R7延岡工業_図面.pdf（令和7年度 学校施設台帳）",
    "updatedAt": "2026-09-09"
  },
  "buildings": [ ... ],
  "nodes": [ ... ],
  "edges": [ ... ],
  "destinations": [ ... ]
}
```

### 3.2 建物

```ts
interface Building {
  id: string;        // "b1"
  name: string;      // "管理・教室棟"
  planCode: string;  // 図面の建物符号 "①"
  planPage: number;  // 図面のページ番号（出典を追えるように）
  floors: number[];  // [1, 2, 3]
}
```

### 3.3 ノード

```ts
interface Node {
  id: string;        // "n001" 不変ID（QRのURLに焼くので絶対に変えない）
  label: string;     // "事務室前"
  kind: "room" | "corner" | "stair" | "bridge" | "entrance";
  building: string;  // Building.id
  floor: number;
  x: number;         // 図面座標（m）
  y: number;         // 図面座標（m）
  source: "plan" | "survey";   // 図面から起こした値か、現地実測で直した値か
  qr?: {
    place: string;   // "事務室窓口の右の柱"
    facing: number;  // QRを正面に見たとき利用者が向く実方位（現地実測）
  };
  landmark?: { text: string; photo?: string };
}
```

**`source` フィールドの意味**: 図面由来か実測由来かを区別する。
現地で直した箇所が一目で分かり、検証データの集計にも使える。

**`x`, `y` は廊下上の点を指す。** 部屋そのものの中心ではなく、
「その部屋の前の廊下」の座標を入れる（経路は廊下を通るため）。

### 3.4 エッジ

```ts
interface Edge {
  from: string;
  to: string;
  kind: "corridor" | "bridge" | "stair" | "door";
  /** 階段のみ: 上り +1 / 下り -1。省略時は同一階 */
  floorChange?: number;
  /** 案内文の上書き（省略時は自動生成） */
  instruction?: string;
}
```

**方位も距離も持たない。** 両端ノードの座標から計算する。
双方向として扱う（逆向きは方位に180度足す）。

### 3.5 目的地

```ts
interface Destination {
  nodeId: string;
  displayName: string;
  category: string;
  order: number;
  note?: string;
}
```

**案内先を増やすときは、このリストにエントリを足すだけで済むこと。**
コード側に目的地の名前や数を埋め込まない。

## 7. 現地検証モードの設計

図面から起こしたデータを現地で確かめ、ズレを直すためのツール。
**ゼロから測るのではなく、答え合わせをする道具。**

### 7.1 機能

| 機能 | 内容 |
|---|---|
| 方位検証 | 廊下に立ち、進行方向を向いて記録。図面から計算した方位との差を表示 |
| planUpBearing 補正 | 複数地点の測定結果から、図面全体の回転角を推定して1つの値に補正する |
| QR facing 記録 | QR掲示位置で「QRを正面に見た向き」を実測して保存 |
| 目印の記録 | 写真撮影＋メモ |
| 距離の抜き取り検証 | 歩数カウント（またはメジャー）で図面値との誤差を確認 |
| 座標の手直し | 図面と実際が違う箇所（増改築など）を修正 |
| 誤差ログ | 測定値と図面値の差を全件記録し、CSVで書き出す（検証データになる） |

### 7.2 方位検証のフロー

```
[1] 検証する区間を選ぶ（例: 事務室前 → 校長室前）
       |
[2] その区間の図面計算値を表示（例: 「図面では 135度（南東）」）
       |
[3] 実際に進行方向を向いて「記録」をタップ
       -> 3秒サンプリング -> 中央値
       |
[4] 差を表示（例: 「実測 142度 / 図面 135度 / 差 +7度」）
       |
[5] 記録して次へ。全区間の差の平均が planUpBearing の補正値になる
```

### 7.3 角度の中央値

方位は円環データなので単純平均は使えない。
最頻方向を基準に ±180度 へ正規化してから中央値を取る。

```ts
function circularMedian(degrees: number[]): number {
  if (degrees.length === 0) return 0;
  const base = degrees[0];
  const norm = degrees.map((d) => ((d - base + 540) % 360) - 180);
  norm.sort((a, b) => a - b);
  const mid = norm.length % 2
    ? norm[(norm.length - 1) / 2]
    : (norm[norm.length / 2 - 1] + norm[norm.length / 2]) / 2;
  return ((base + mid) % 360 + 360) % 360;
}
```

### 7.4 センサーの取得

```
iOS     : webkitCompassHeading（真北基準）。DeviceOrientationEvent.requestPermission() が必要
Android : deviceorientationabsolute の alpha（360 - alpha が方位）
```

**権限が取れない場合も必ず動くこと。** 手動入力欄を用意する。

### 7.5 データの保持

```ts
const KEY_DRAFT = "arnav.draft";       // 現地での修正内容
const KEY_MEASURE = "arnav.measures";  // 測定ログ（検証データ）
```

操作のたびに localStorage へ保存する。現地でアプリが落ちても記録を失わない。

### 7.6 データの往復

```
スマホで検証 -> localStorage
  -> #/admin/data で「JSONをダウンロード」
  -> 自分宛に送信 or クラウドストレージ経由
  -> PCで campus.json を更新 -> git push -> Cloudflare Pages が自動デプロイ
```

図面ベースになったことで現地での修正量が少ないため、
Cloudflare KV による端末間同期は**後回しでよい**（必要になったら追加する）。

## 8. 経路探索

### 8.1 アルゴリズム

ダイクストラ法。ノード数100程度なので性能上の問題はない。

### 8.2 コスト

```ts
const edgeCost = (e: Edge, dist: number) => {
  switch (e.kind) {
    case "corridor": return dist;
    case "bridge":   return dist * 1.1;   // 渡り廊下はやや避ける（雨天考慮）
    case "stair":    return 25;           // 階段1階分 = 25m相当
    case "door":     return 3;
  }
};
```

### 8.3 案内文の自動生成

連続するエッジの方位差から曲がる方向を判定する。

```ts
function turnInstruction(prev: number, next: number): string {
  const diff = ((next - prev + 540) % 360) - 180; // -180〜180
  if (Math.abs(diff) < 20) return "そのまま直進";
  if (diff >= 20 && diff < 160) return "右に曲がる";
  if (diff <= -20 && diff > -160) return "左に曲がる";
  return "後ろに戻る";
}
```

**連続する直進区間は1ステップにまとめる。**

生成例（事務室前 → 職員室前）:

```
1. 廊下をまっすぐ 約23m 進む（校長室を過ぎます）
2. 右手が職員室です
```

|---|---|---|
| **Cloudflare Pages** | **採用** | GitHub連携で push→自動ビルド。**ビルドがCloudflare側で走る**ため、校内PCのプロキシ・ポータブルNode環境の制約を受けない |
| Cloudflare Tunnel + RPi | 却下 | 校内ネットワークで cloudflared が遮断される（2026-07-08検証済み） |
| GitHub Pages | 次点 | 動作実績あり。ただしローカルで `npm run deploy` が必要 |

### 10.2 セットアップ

```
1. GitHub にリポジトリを push（junpei-dev/ARmap の main ブランチ）
2. Cloudflare -> Workers & Pages -> Create -> Pages -> Connect to Git
3. ビルド設定:
     Framework preset : Vite
     Build command    : npm run build
     Build output dir : dist
4. https://armap.201536-teacher.workers.dev で公開
```

`vite.config.ts` の `base` は `"/"`（Pages はルート配信）。

## 12. 技術選定

| 領域 | 採用 | 理由 |
|---|---|---|
| フレームワーク | React 19 + TypeScript | 前回実績あり |
| ビルド | Vite 6 | Cloudflare Pages のプリセットあり |
| ルーティング | 自前のハッシュルータ | 依存を増やさない |
| QR読取 | jsQR | WASM不要。前回実績あり |
| QR生成 | qrcode | 同上 |
| AR | **ライブラリ不使用** | `getUserMedia` + Canvas + CSS transform のみ |
| 状態管理 | React 標準 | この規模でライブラリは過剰 |
| CSS | 素のCSS | Tailwind を持ち込む価値がない規模 |
| ホスティング | Cloudflare Pages | 10.1節 |

### 意図的に採用しないもの

- **MindAR / A-Frame / three.js**: 日本語が描画できず、照明条件に弱い。前回この判断で作り直している
- **WebXR**: iPhone Safari 非対応
- **PWA / Service Worker**: キャッシュ絡みの不具合リスクの方が大きい
- **バックエンドDB**: 経路データは読み取り専用。静的JSONで足りる

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| `planUpBearing` が実際とズレている | **全ルートの矢印が同じだけ狂う** | 現地検証で最優先に確認。1つの値を直せば全体が直る |
| 図面と現況が違う（増改築・部屋の用途変更） | 案内が間違う | 現地検証で該当ノードだけ `source: "survey"` にして修正 |
| 棟の相対位置が配置図から正確に取れない | 棟をまたぐ経路の方位が狂う | 棟の接続点（渡り廊下）で方位を実測して合わせ込む |
| 磁気の乱れで検証値が信用できない | 補正を誤る | 複数地点の測定値の中央値を使う。外れ値は捨てる |
| iOS の権限拒否 | AR案内が成立しない | QRの `facing` を基準にするフォールバックを用意済み |
| QRのURLを後から変更したくなる | 印刷し直し | ドメインを最初に確定。ID対応表を残す |
